LAN 分段与准入：从 VLAN 到 SGT 的三层粒度

这一章是全书篇幅最大、配置细节最密的一章。核心问题只有一个： 怎么把「谁能跟谁通信」这件事表达清楚——用 VLAN 表达是粗粒度， 用 Group Policy 表达是按身份，用 SGT 表达才能做到同网段内的微隔离。

技术密度：极高 篇幅最大：143 页 面试高频：分段 / stateless ACL / SGT
i

标注约定：（p.xx） 为书中原文位置；（推论） 为基于机制的推演，书里没明说。 书中未涉及的部分直接标「书中未涉及」——本章有几处常见的说法（比如 WPA2/WPA3 四次握手对比） 书里其实没有讲，我不会替它补。

一、设计理念：三种粒度，各管一段

Meraki 在 LAN 侧给了三套表达方式，很多人把它们混着用，结果策略互相打架。 理解它们各自解决什么、在哪一层执行，是这一章最重要的事。

手段粒度在哪执行能解决解决不了
VLAN 整个广播域 全链路（需要每台设备透传） 广播域隔离、按物理位置划片 同 VLAN 内互访；频繁变更（改一次要动全线）
Group Policy 按客户端身份 交换机 / AP / MX 同一 SSID 或同一端口，按身份落到不同 VLAN + 不同 L3/L7 策略 同一 VLAN 内的主机互访（p.517）
Adaptive Policy（SGT） 按标签，可跨网段 egress（交换机侧强制） 同网段内微隔离、跨 WAN 保持标签 强制点不在 MX 上（p.510）

1.1 为什么需要 Group Policy：一个真实约束

书里给的动机很具体（p.475）：小型零售门店需要隔离卡支付流量， 但不能改变用户的操作方式。传统做法是「一个场景一个 VLAN / 一个 SSID」， 结果是 SSID 越堆越多、用户选错网络。Group Policy 的做法是 一个 SSID 按组下发不同 VLAN，把拆分从「用户要选」变成「策略自动决定」。

这条设计正好对应 NIST 800-53 的 AC-4(21)——信息流分离。 注意这里是合规要求驱动了功能设计，不是反过来。

!

部署形态会影响能力上限：Group Policy 只在 network 级配置，且没有默认策略。 官方建议部署完整的 Meraki stack（Wi-Fi + switching + MX）以获得最广能力， 因为各平台支持的特性差异很大——例如 MS 不支持 VLAN tagging / scheduling / L7 规则（p.475-476）。

1.2 为什么无线侧把防火墙放在 AP 上

作者对 MR 上直接做 firewall 的评价是 quite unique（p.384）。 动机是：在基础设施很少的场景下也能获得细粒度控制—— 一个只有几台 AP、没有本地 MX 的小办公室，也能在 AP 上拦住到内网的流量。

MR 的默认策略也体现了这个定位（p.389）：拒绝到 local LAN（RFC 1918 网段），放行其他。 这正好适配 Guest Wi-Fi 场景——访客不能碰内网，但能上网； 而 VLAN 之间的管控继续交给本地 MX。

1.3 端口安全：来自合规的一条硬要求

端口安全特性的动机在书里指向 NIST 800-53 9.2.2： 限制公共可达的网络插口（p.393）。典型场景是机房走廊的 IP 电话口、机场和商场里已布线但未使用的面板。 书里的建议很直接：端口没有正当用途就直接 disable。

1.4 Port isolation：为「只该上网」的设备准备

定位是额外一层防护（p.399），三个典型场景： 只应访问 Internet 的设备（书里举例 Meraki MV 摄像头）、IoT 同 VLAN 内防横向移动、DMZ。 共同特征是——同 VLAN 是因为功能或安全级别相同，但并不需要 east-west 通信。

1.5 SecurePort：把基础设施也纳入零信任

设计意图是让 AP 这类基础设施设备也走「验证后才能接入」的流程， 用的是既有的硬件信任模型而非证书（p.402）。 运维收益很实际：无需管理证书，也无需手工配置 AP 所在的交换端口。

二、机制拆解：包在哪一层被判断

2.1 stateless ACL 到底意味着什么

Meraki 有线侧的默认状态是「switches 默认 allow all + stateless ACL」，书里明说这属于基本功能（p.384-385）。 stateless 的含义是：设备不维护会话表，每条规则独立匹配单个方向的报文。

直接后果是——如果你写了一条 deny any，就必须另写一条规则显式放行回程流量（p.385）。 书里用 packet capture 验证了这一点：只有 echo request 到达，echo reply 被丢掉（p.389-390）。

◆

面试可直接引用：「Meraki 的 ACL 和 MR 防火墙都是 stateless， deny 之后回程要显式放行，验证方式是抓包看只有单向流量。」 这句话能同时证明你配过、也排过。

2.2 MR 最容易踩的一个坑：L3 放行后不再过 L7

这是本章专门加 Note 强调的反直觉之处（p.389）： 被非默认 L3 规则 permit 的流，不会再次被 L7 规则评估。 而 MX 会在 L7 阶段重新评估。

（推论）这意味着同样的策略意图，在 MX 上写和在 MR 上写，结果可能相反： 你在 MR 上先写了一条宽松的 L3 permit，再精心配的 L7 应用封禁可能根本不生效。 迁移策略时不能照搬。

2.3 NBAR：L7 识别是怎么做到的

MR 的 L7 依赖 NBAR（p.391-392），条件是 Wi-Fi 6 及以后的 AP + MR27 以上固件， 可识别 1500+ 应用。匹配维度可以是内容类别、HTTP hostname、端口、远端 IP 段，或它们的组合。

但有一个体验缺陷（p.391）：L7 封 HTTPS 站点不会给用户 block page。 用户看到的是连接被重置。想要友好提示页，得依赖 Secure Connect。

2.4 SGT：把标签贴进报文里

书里用了一个很好的类比（p.492）：SGT 类似 QoS marking 或 MPLS label—— 通常贴近源端打标，后续每一跳只看标签快速查表决定处理方式，不做逐包深度检查。

技术实现上，SGT 被加入报文的 IP header，封装在 EtherType Cisco MetaData (CMD) 内（p.492）。

打标方式位置限制
SSID 静态指定 adaptive policy groupWireless 配置仅限启用 RADIUS 的 SSID
Switch port 静态指定 adaptive policy groupSwitching 配置—
Cisco ISE 在 802.1X 授权结果中动态下发 Security GroupRADIUS 授权需要 ISE 与 802.1X 全链路就绪

依据：p.493-508

几个必须一起记住的配套条件：

  • 交换机侧要把上联口和 AP 口设为 Peer SGT Capable，否则标签传不出去（p.493-508）
  • SGT 2 是内置的 Infrastructure 专用标签，不要占用（p.493-508）
  • 策略在 organization 级配置，规则基于 SGT 而非 IP，在 egress 执行——检查源/目的标签后 allow 或 deny（p.510）
  • 默认 adaptive policy 放行所有流量，也就是说开了功能不等于有策略（p.510）
  • SGT 的强制点目前不在 MX 本身，所以建议客户端都接交换机或 AP（p.510）
  • 跨 WAN 可保持标签：MX 在 Routed 模式 Auto VPN 下可 preserve / propagate SGT；但 LAN 口与 VPN 上的 SGT 传播默认关闭，需手工开启（p.494）

2.5 Group Policy 的分配方式是有平台差异的

这一点在选型时经常被忽略——同一个「Group Policy」，在不同平台上支持的分配维度并不一样（p.479）：

by device type支持——仅 AP

by AD group支持，但需要 Advanced Security License—
by clientMS 不支持 by client / by VLAN按 MAC 识别，见下方坑

2.6 DAI：用 DHCP 表校验 ARP

DAI（Dynamic ARP Inspection）的机制（p.404-405）： 交换机为每个端口维护 trust 状态，对 untrusted 端口上的 ARP 报文与 DHCP snooping 表做比对，不符即丢弃，从而避免 ARP cache 被改写。

默认所有端口都是 untrusted；书里建议只把上联口和静态 IP 设备所在端口设为 trusted。 它拦的是 ARP 投毒型中间人攻击——攻击者冒充网关，把流量引到自己身上。

2.7 Rogue DHCP：一张允许清单

机制（p.408-410）：Dashboard 会记录网络中出现过的 DHCP server 列表； 把策略设为 IPv4 Default Policy = Block DHCP Servers， 再把合法 server 的 MAC 放进 Allowed DHCPv4 Servers。 未知 server 的响应被丢弃，并产生 DHCP Blocked 事件。IPv6 逻辑相同。

靠一张 MAC 允许清单就挡住了「随便插一台 DHCP 就能把整个子网搞瘫」这类事故，成本极低、收益极高。

2.8 SecurePort：一条四步的信任链

AP 首次接入时（p.402），流程是：

  1. 端口只放通到 Meraki Dashboard 的流量——先把「找妈妈」的路留出来
  2. AP 下载证书与配置
  3. AP 发起 802.1X，交换机拿证书向 Meraki Cloud 校验，并确认与自己在同一 organization
  4. 端口自动放开

如果换成非 Meraki 设备插上去，端口回到初始配置——不会因为「有人插了台交换机」就把网络打开。 这是把基础设施接入也纳入零信任的典型做法。

2.9 Port isolation：只在本机生效的二层隔离

机制是阻止同一交换机、同一 VLAN 内的设备互访（p.399-400）。三个限制必须一起记：

  • 只在本交换机生效，跨交换机无效
  • 跨交换机场景需要把 downlink 口和所有 host 口都设 isolation
  • 绝不能把 northbound uplink 设成 isolation，否则主机根本出不了交换机

2.10 WPA3 192-bit：具体用了哪些算法

这是全书少见的、把密码学套件写清楚的地方（p.520-521）：

书中未涉及 WPA2 与 WPA3 的四次握手差异、SAE 与 PSK 的对比。 这部分属于协议层知识，书里只给了上面这套套件参数。

2.11 Air Marshal：WIDS/WIPS 的代价

告警分三类（p.521）：

  • 接入网络的 rogue AP
  • 伪造你的 SSID 或 AP 的设备（钓鱼热点）
  • 恶意广播与 packet flood

该功能默认启用。但有一个性能代价必须知道： 没有专用扫描 radio 的 AP，必须短暂 off-channel 才能扫描，而 off-channel 期间无法服务客户端。 所以书里推荐使用带专用扫描 radio 的型号以保住性能。

书中未涉及 containment 的具体动作（例如是否发 deauth 帧）， 也未给出 rogue AP 的判定算法——只给了「接入网络 / 伪造 SSID」这两类依据。

三、书中的实验

3.1 SGT 微隔离：同网段互 ping 失败是怎么做到的

这是本章最能说明问题的一个实验（p.511-519）。布景：

  • Staff 笔记本 192.168.168.8，SGT 10
  • POS 终端 192.168.168.7，SGT 20（与 Staff 同一网段）
  • 另一端站点的 POS server 192.168.98.2，SGT 20

adaptive policy 设 Staff → POS = Deny，结果：

  • 同网段内互 ping 失败——这是 VLAN 方案做不到的
  • 跨 WAN 到 POS server 也失败——标签跟着隧道传过去了
  • 但两端各自网关正常、POS 终端 → POS server 通信正常——策略只精确命中 Staff→POS 这一对
  • packet capture 显示单向 ICMP，证明是 egress 丢包

这个实验同时证明了三件事：微隔离可行、跨 WAN 标签可保持、丢包点是 egress。 面试里如果被问「怎么在同一网段里做隔离」，这就是标准答案的具体化。

3.2 Group Policy：同一个 SSID 换 VLAN

建一个 Staff group policy，Wireless Only 指定 VLAN 127， 并加一条 L7 规则封 eBay。分配到客户端后，Clients 页显示该客户端 VLAN 由 130 变为 127， 同时 www.ebay.com 打不开（p.478-482）。

注意这里同时改了两件事：二层归属（VLAN）和七层策略（L7 规则）—— 这正是 Group Policy 存在的意义：一次分配，同时决定「在哪个网段」和「能访问什么」。

3.3 Rogue DHCP：一条事件日志定位到端口

IPv4 由直连 MS 的 MX 提供。策略设为 Block DHCP Servers 并允许合法 MAC 后， 在 rogue server 同 VLAN 的客户端上执行 ipconfig /release + /renew， 事件日志出现 DHCP Blocked，点 Client 列的 MAC 就能定位到 「Bondi 分支 Bondi-G-MS120-1 的 port 4」（p.408-410）。

这个例子的价值不在配置，而在可观测性： 拦截动作直接产出一条带端口位置的事件，而不是让运维去猜谁的网段出了问题。

3.4 Port isolation：两台摄像头

两台同网段的 Meraki MV 摄像头（192.168.200.2 / 192.168.200.6）， 启用 isolation 后，前者仍能 ping 8.8.8.8，但 ping 同网段另一台失败（p.401）。 一个配置同时达成了「能上网」和「不能横向移动」。

3.5 EAP-TLS 全流程：把 PKI 的成本压到最低

EAP-TLS 的门槛一直是证书管理，书里的做法是用 ISE 当 CA 加 Systems Manager 自动推送（p.429-446）：

  1. ISE 身份源序列勾 Certificate Based Authentication
  2. 复制 Allowed Protocols 为 EAP-TLS and PEAP Only，设 Preferred EAP Protocol = EAP-TLS
  3. 在 policy set 插入 EAP-TLS 规则并绑定 Certificate_Request_Sequence
  4. 用 Certificate Provisioning Portal 签发用户证书，导出 ISE EAP CA 证书
  5. 由 Systems Manager 推送证书 + Wi-Fi/Ethernet profile

客户端最终显示 Authenticated via EAP-TLS。整套下来用户零操作， 这就是「双向证书认证在 Meraki 上可以工程化落地」的证明。

3.6 Sentry Wi-Fi / Sentry LAN：把 EAP-TLS 简化成打 tag

书中给了两条路（p.447-457）： SSID 侧选 Enterprise With + Meraki Cloud Authentication， 然后 Add Sentry Network 按 Scope/Tags 匹配 Systems Manager 设备； 有线侧建 Access Policy = Meraki Authentication + Systems Manager Sentry Security（按 tag scope），再套到端口。

用户不用输账号密码，只需点 OK 选证书即以 EAP-TLS 上线。 作者的判断是：证书与 CA 都由 SM 自动下发后，任何规模的网络都没理由再不做双向 802.1X（p.457）。

!

但这功能要谨慎对待：书中自称 Sentry LAN 属于 undocumented feature， 需要自行验证（示例环境 macOS 14.5 + MS120 16.7）。上生产前必须自己压测（p.451）。

五、面试问答

Q1：要在同一个网段里隔离两台主机，怎么做？

一句话：VLAN 做不到，要用 Adaptive Policy + SGT——标签贴在报文的 IP header 里（CMD EtherType）， 策略在 egress 按源/目的标签放行或拒绝（p.492、p.510）。

可展开：打标可在 SSID、交换机端口静态指定，或由 ISE 在 802.1X 授权结果里动态下发； 上联口与 AP 口要设 Peer SGT Capable 才能透传；SGT 2 是内置 Infrastructure 标签； 默认 adaptive policy 放行所有流量，所以开了功能还得写策略；强制点不在 MX。

Q2：VLAN、Group Policy、SGT 该怎么选？

一句话：VLAN 划广播域，Group Policy 按身份决定「落哪个 VLAN + 什么策略」， SGT 解决同 VLAN 内的微隔离（p.475、p.510、p.517）。

可展开：判断标准是「隔离边界是否与网段边界重合」。 重合就用 VLAN；不重合但能接受换网段就用 Group Policy； 完全不重合又必须同网段（比如同一台服务器的不同服务、POS 与办公终端同段）就只能上 SGT。 代价是 SGT 对硬件和授权要求最苛刻。

Q3：stateless ACL 会带来什么问题？

一句话：不维护会话表，所以 deny any 之后回程流量也要显式放行； 验证方式是抓包看到只有单向报文（p.385、p.389-390）。

可展开：这会影响规则编写习惯——写规则时要成对思考方向； 排障时「ping 不通但规则没拦」往往就是只放行了去程。组策略与无线防火墙里的 L3/L7 同样是 stateless。

Q4：DAI 和 Rogue DHCP 防护分别防什么？

一句话：DAI 用 DHCP snooping 表校验 untrusted 端口上的 ARP，拦 ARP 投毒型 MITM； Rogue DHCP 只允许白名单里的 DHCP server 应答，拦「插一台 DHCP 就把子网搞瘫」（p.404、p.408）。

可展开：两者都依赖 DHCP snooping 建立的信任表； DAI 默认所有端口 untrusted，只把上联和静态 IP 设备口设 trusted； Rogue DHCP 的拦截会产出带端口位置的 DHCP Blocked 事件，这点在排障时很有用。

Q5：SecurePort 是什么？为什么不用证书？

一句话：AP 首次接入时端口只放通到 Dashboard 的流量，AP 下载证书后再做 802.1X， 交换机向 Meraki Cloud 校验证书并确认同 organization，然后端口自动放开（p.402）。

可展开：运维收益是无需管理证书、无需手工配置 AP 所在的交换端口； 换成非 Meraki 设备则端口回到初始配置。它用既有的硬件信任模型替代了 PKI 管理成本。

Q6：WPA3 192-bit 模式用了什么算法？

一句话：EAP-TLS 用 ECDH + ECDSA（384-bit 曲线），加密 GCMP-256， 密钥派生与确认 HMAC-SHA384，管理帧保护 BIP-GMAC-256（p.520-521）。

可展开：硬件要求 802.11ac Wave-2 以上 + MR27 以上固件； 驱动因素是 PCI DSS 4.0 4.2.1.2 要求认证与传输使用强加密。 注意书里没讲四次握手与 SAE 的细节，被追问协议层时要说明这属于 RFC 范畴。

Q7：Air Marshal 开了有什么代价？

一句话：没有专用扫描 radio 的 AP 必须短暂 off-channel 才能扫描，期间无法服务客户端， 所以要选带专用扫描 radio 的型号（p.521）。

可展开：它检测三类情况——接入网络的 rogue AP、伪造你 SSID 的设备、 恶意广播与 packet flood；默认启用；对应 PCI DSS 11.2.1 对「定期发现并区分授权/未授权 AP」的要求。

本章最该记住的一句判断： 分段手段的选择标准不是「哪个更安全」，而是「隔离边界是否与网段边界重合」。 重合 → VLAN；不重合但可换网段 → Group Policy；不重合且必须同网段 → SGT。
