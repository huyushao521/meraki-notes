第 11 章 · 深度精读

终端安全：检查 → 下发 → 闭环

前四章的控制点都在网络上：谁能进网、网内怎么分段、出网怎么检查。 这一章把控制点挪到了设备自己身上——因为混合办公之后，员工大部分时间根本不在你的网里。 Systems Manager 的价值不是"能配多少策略"，而是它把审计（发现不合规）与 修复（下发证书 / 配置 / 软件）放在了同一个控制台里，还能跟 Sentry 准入打通。

技术密度：高 篇幅：41 页（p.710-750） 面试高频：策略 vs 配置 / EAP-TLS 发证 / supervised 边界
i

标注约定：（p.xx） 为书中原文位置；（推论） 为机制推演。 本章实操步骤极多，我把它们整理成 18 个案例，每个按「场景 → 动作 → 现象 → 坑 → 面试怎么用」写， 关键字段保留界面上的英文原名，方便照着点。

一、设计理念：为什么终端要单独成章

1.1 控制点的三次漂移

把这一章放回全书的位置看，会看到一条很清晰的线：

章节控制点在哪它回答的问题失效场景
Ch7 身份 人 你是谁，凭什么证明 设备本身带毒，人却是合法的
Ch8 LAN 交换机 / AP 端口 这台设备能不能进这个网段 设备在家、在咖啡厅，根本不碰你的端口
Ch9 WAN 隧道与出口 站点之间怎么连、远端怎么接 SaaS 流量直接出公网，不经过你的出口
Ch10 流量 路径上的检查链 穿过的流量能不能放行 端点自己已经被攻陷，流量看起来完全合法
Ch11 终端 设备本身 这台设备的姿态是否可信 —（这是最后一层，也是唯一跟人一起移动的一层）

所以本章开头那句「混合办公时代端点安全可能从未如此重要」不是套话： 前四章的所有控制都有一个共同前提——流量要经过你。而终端安全是唯一不依赖这个前提的一层。

1.2 SM 与 Duo 的分工：管与报 vs 拦与警

书里用一整段讲这件事（p.710-711），因为这是最容易讲错的面试点：

Meraki Systems Manager

云托管 MDM。管 Android / ChromeOS / iOS / tvOS / macOS / Windows。 能做的是报告（最低 OS 版本、有无强装/禁装应用、是否越狱、有无 passcode、是否按周期 check-in） 与推送（配置 payload、证书、应用、OS 更新）。 本质是异步的管理面：它改变设备的未来状态，不是拦住当下的连接。

Cisco Duo

同步的准入面。连接发生时判断设备是否可信，可以提示用户升级， 最终直接阻断网络访问直到设备达标。 它不负责把设备修好，只负责"不达标就不让进"。

两者覆盖的是同一批属性（补丁版本、屏幕锁、磁盘加密、passcode）， 所以书里把它定义为 defense-in-depth：同一份策略，一个负责报告和管理，一个负责强制执行（p.711）。

◆

一句话记住分工：SM 管与报，Duo 拦与警。 面试如果被问「有了 Duo 还需要 MDM 吗」，正确的回答是：Duo 只能让设备进不来， 但进不来的员工还是没法工作；MDM 才能把设备修到达标。反过来只有 MDM 也不行， 因为报告依赖用户自觉，强制力必须由准入侧提供。

1.3 最被低估的设计：Sentry 与 SM 打通

书里说选择 SM 而不是竞品的关键理由是它带来的 Sentry 系策略（p.710），落点很具体： Ch8 的 Sentry Wi-Fi / LAN、Ch9 的 Sentry VPN 只要几次点击就能上线， 而其中「用证书做 EAP-TLS 入网」这件事，传统做法需要一套 PKI + 人工分发证书 + 用户手动装描述文件， 现在变成 Meraki 自有 CA 自动签发 + SM 自动推送 + 用户零交互连上（p.722、p.724-730）。

!

反过来看这条设计的真正目的：不是省事，是消灭影子 IT。 书里明确写过：如果入网流程太麻烦，用户就会去找开放 SSID、自己插一个家用路由器（p.722）。 所以"零交互入网"是一项安全控制：流程越顺，用户绕过它的动机越小。 面试里把这一点讲出来，比背配置项得分高得多。

二、机制拆解

2.1 控制平面：APNS 静默通知 + 拉取，而不是长连接

这是理解 SM 一切"延迟"现象的根：

书上写的链路（p.711）：Apple 的 Push Notification Service 先给设备发一条静默通知 → 设备被唤醒后向 Meraki Dashboard check-in → 取回待执行的命令。

推论出来的三个性质： ① SM 不能主动连设备，只能"敲门"，所以命令是最终一致而非实时； ② 设备离线时命令排队，上线后补执行——所以你会看到"昨天点的 Push 今天才生效"； ③ 整条链路依赖 Dashboard 里那张 Apple push 证书，证书过期 = 所有 Apple 设备失联， 这是运维里最经典的定时炸弹。

证书本身的信任模型是：Meraki 生成 CSR → 你拿 Apple ID 去 identity.apple.com/pushcert 换取签名后的 .pem → 传回 Dashboard（p.712-714）。注意 Apple ID 必须开两步验证（p.712）， 而且下载回来的文件名里带 MDM–Meraki Inc.–Certificate.pem， 面试里被问"为什么 MDM 需要一张证书"，标准答案是：它是 Apple 允许某个 MDM 服务器向这台设备下命令的授权凭证。

2.2 四层模型：只读的审计层 + 可写的执行层

本章所有配置项都能塞进下面四层。这张表建议直接背下来，因为它解释了"为什么配了策略设备还是不合规"。

层Dashboard 位置读写属性能做什么不能做什么
Enrollment 准入 Systems Manager > Devices > Add Devices 写（一次性） 把设备纳入管理；决定能力上限（ADE / device owner / managed profile） 手动入 ADE 需恢复出厂，不适用 BYOD（p.715）
Policies 合规审计 Systems Manager > Policies 只读 检查 OS 版本、必装/禁装应用、越狱、passcode、check-in 周期；出合规报告与告警 不下发任何设置或软件（p.716）
Profiles + Payloads 配置下发 Systems Manager > Settings > + Add Profile 写 推证书、Wi-Fi、VPN、passcode、restrictions、FileVault 等设置 只对 Scope 命中的设备生效
Apps + Commands 软件与命令 Systems Manager > Apps / Devices 写 推送应用（可静默）、推 OS 更新、下发远程命令 OS 更新需 ADE + supervised（p.748）
◆

这条"只读/可写"的分界是本章的主线。书里还给了操作顺序建议：先配 policy，再配 profile（p.716）。 原因是 policy 定义了"达标长什么样"，profile 才是把它做出来的手段； 先有度量标准再改配置，才能用同一张合规报表证明改动有效——这就是案例 13 那个"不合规 → 自动回归合规"的闭环。

2.3 Scope 的七个维度：策略作用域本身就是一种控制

创建 profile 时最容易被当成"随便选一下"的一步，其实决定了整套策略的表达能力（p.721-722）：

  • 全部设备 / 带某个 tag 的设备 / 不带某个 tag 的设备（书里例子用 Store-device）
  • 用户所在位置
  • 设备是否已经符合安全策略（合规才下发某些宽松配置）
  • 时间段
  • 设备所有者是谁

书里还给了两条容易被忽略的工程建议：每个操作系统单独一个 profile（同一条 passcode 策略在 iOS 和 macOS 上的解释完全不同）， 以及用 Description 字段记录创建者/修改者的姓名缩写 + 变更摘要做版本控制（p.721）。

2.4 EAP-TLS 的两张证书：一张证明我是谁，一张决定我信谁

这是本章技术含量最高、也最容易在面试里被追问到底的细节。书里的 Wi-Fi payload 里有两个必填项（p.724-730）， 二者缺一不可，而且作用完全相反：

字段放什么解决什么问题放错的后果
Identity Certificate ISE Certificate Provisioning Portal 签发的设备证书 向 AP / ISE 证明这台设备是谁（客户端侧身份） 没有它就只能退回 PEAP 用户名密码，失去 EAP-TLS 的意义
Trusted Certificates ISE CA 证书（书里 CN 为 ise.selab.local） 让设备判断对面那个 RADIUS 是不是真的（服务端侧验证） 下拉框里什么都没有可选——因为信任锚没被推下去（p.726）

对比 Ch7 讲的 PEAP：PEAP 只验服务端、客户端交密码，是单向信任； EAP-TLS 两边都出示证书，是双向信任，也是它能做到"零用户交互"的根本原因—— 没有密码要输，就没有交互可做。书里在设备上点开 profile 时，能看到 WI-FI NETWORK 下同时列出 SSID 与所需证书（p.727），最后在 ISE live logs 里确认协议确实是 EAP-TLS（p.729）。

2.5 supervised 与否，是能力的分水岭

能力supervised（ADE 注册）非 supervised依据
按名字隐藏指定 App 可以（Show or Hide Apps） 不可以，只能按 age rating 限制 p.739、p.741
推送 OS 更新 可以 不可以 p.748
设备到达即已注册 可以（ADE 自动） 需用户手动 enroll p.714-715
BYOD 可用性 不可（需恢复出厂） 可以；Android 还可走 managed profile mode 容器化工作数据 p.715
!

代价说清楚：supervised 的能力来自"公司拥有这台设备"这个前提， 而开启 supervised 的手动路径必须恢复出厂。所以这是一个所有权与能力的交换， 不是纯技术选择——所以在方案里必须按设备归属分池：公司资产走 ADE + supervised， 个人设备走 BYOD + managed profile mode，两套 profile，两套策略。

三、案例库（18 个，可复现）

下面每个案例都按「场景 → 动作 → 现象 → 坑 → 面试怎么用」组织。 前 9 个是"把系统搭起来"的骨架，后 9 个是"真正产生安全效果"的落地案例。

案例 1 · 打通 Apple 通道：装 push 证书（一切的前提）

场景：刚拿到 SM 许可，一台 Apple 设备都还没有，什么都不可能做。

动作：Organization > MDM（Configure 下）→ Apple MDM Push Certificate > + Add Certificate → 下载 Meraki–Apple–CSR.csr → 点 Apple Push Certificate Portal 登录 identity.apple.com/pushcert（需两步验证）→ Create a Certificate → 勾同意条款 → Choose File 选 CSR → Upload → 下载 MDM–Meraki Inc.–Certificate.pem → 回 Dashboard 填 Apple ID、拖入 pem、Add（p.711-714）。

现象：MDM Settings 页出现 CURRENT APPLE MDM PUSH CERTIFICATE 区块及证书详情（p.714，图 11-6）。

坑（书上明写的）：上传 CSR 报错时，切回旧版 MDM Settings 页面重新下载 CSR 即可（p.713）。 这类"新版界面有 bug，回退旧版"的提示在书中极少出现，属于可以当经验讲的细节。

面试怎么用：被问 MDM 的通信原理时，从这张证书讲起—— 不是"云平台直接连设备"，而是"平台拿 Apple 授权的凭证，通过 APNS 敲门，设备回头来取命令"。

案例 2 · 手动 enroll 一台 iPad（并说明为什么生产环境不这么干）

场景：书里所有 Apple 侧的演示，都是用手动注册的一台 iPad 完成的（p.715）。

动作：Systems Manager > Devices > Add Devices 按提示生成注册入口； 用户侧完成认证。默认认证方式是 Meraki Cloud 认证， 生产环境应改为 SAML / Entra / ISE / Duo（Systems Manager > General > End User Authentication Settings，p.715）。

现象：设备出现在 Devices 列表，开始上报数据、可接收 profile 与远程命令（p.714-715）。

坑：注册这一步决定了后面所有能力上限。手动注册的设备是非 supervised， 于是案例 12 的"按名字隐藏 App"和案例 15 的"推 OS 更新"都用不了—— 很多人以为这是配置没找对，其实是注册方式选错了。

面试怎么用："MDM 的能力边界在注册那一刻就定了"， 这句话能立刻把"会用界面"和"懂设计"区分开。生产建议：公司资产走 ADE（到货即注册），BYOD 走 Android managed profile mode 或 iOS 手动注册 + 只下发容器级策略。

案例 3 · 用一条策略把五项检查串起来（Corp_Security_Policy）

场景：企业要能回答"哪些设备不符合安全基线、为什么"。

动作：Systems Manager > Policies > + Add New；名称填 Corp_Security_Policy（该字段不允许空格），勾选： ① 已配置 passcode lock；② 未 jailbreak / 未 root； ③ All Devices > Application Block List 加入 TikTok； ④ All Devices > Mandatory Applications 加入 Cisco Secure Client； ⑤ All Devices > Minimum OS Version 设 iOS ≥ 17.1（可对不同 OS 分别设）； ⑥ check-in 周期 ≤ 30 天 → Save Changes（p.717-718）。

现象：Devices 列表开始出现合规 / 不合规状态。

坑：应用白/黑名单是靠应用名自动解析成 bundle ID 的，而 bundle ID 未必直观（p.717）； 名字拼写漂移会导致策略形同虚设。另外 30 天这个 check-in 闸门的作用是发现失联设备——丢了、被偷了、 或者用户自己把 SM 描述文件删了（p.718），这条检查就是唯一能看见这些情况的传感器。

面试怎么用：六项检查正好对上一组标准条款： passcode ↔ NIST AC-11，失败擦除 ↔ AC-7(2)，加密 ↔ AC-19，必装 EDR ↔ CSF DE.CM-03， 不可被用户更改 ↔ PCI DSS 4.0 1.5.1，禁装 EOL 软件 ↔ Essential Eight。 把"技术动作 ↔ 合规条款"对上，是从运维视角切到治理视角的最短路径。

案例 4 · 在 Devices 列表里把"为什么不合规"变成一列

场景：报表说某台设备不合规，但不说原因，用户来问就答不上。

动作：Systems Manager > Devices，点 General 右侧的加号自定义列， 勾上合规状态与 Policy Reasons（p.718）。

现象：图 11-8 中两台设备并排显示状态与原因，其中一台因缺 Cisco Secure Client 而不合规（p.718）。

坑（书上明说）：该页有 beta 版本，写作时 beta 版没有 Policy Reasons 列（p.718）。

面试怎么用：合规运营的成本大头不是"定策略"而是"处理例外"。 一个能直接给出原因字段的界面，决定了工单量级别——这是把安全工程讲成业务影响的好素材。

案例 5 · 每日合规报告邮件（以及一个几乎人人踩的收件人坑）

场景：没人天天盯 Dashboard，需要主动推送。

动作：Systems Manager > Alerts→ Enabled Security Reports 配每日邮件，把违反 Corp_Security_Policy 的设备报给管理员 → 页面底部 Save（p.718-719）。

现象：图 11-10 是一份真实报告样例——报告上还是Meraki 原始 logo（作者自己说的彩蛋，p.719）。

坑（书中明确写出，实测最常踩）：如果你按建议给 SM 建了独立网络， 那么 Default Recipients = All Network Admins 不包含 organization admin， 所以你以为配好了、其实一封都收不到。三种修法（p.718-719）： ① 给 SM 网络配 network admins（Systems Manager > General）； ② 在 Additional Recipients 填收件人； ③ 直接在页面顶部 Default Recipients 里加用户。

顺便区分两个词（面试常考）： alert = 检测到合规问题时立即发；report = 按日 / 周 / 月发的汇总摘要（p.719）。

案例 6 · 建第一个 Profile，用 tag 圈定作用域

场景：Acme 有大量门店设备，配置只该发给门店机，不能发给办公室电脑。

动作：Systems Manager > Settings（Manage 下）→ + Add Profile → 保持 Device Profile (Default) → Continue → 填 Name → Scope 选"带 tag Store-device 的设备" → Save（p.720-722）。

现象：profile 建立完成，后续所有 payload 都挂在它下面。

坑 / 工程建议：① 一个 profile 可以只放一个 payload，也可以放一堆——命名时就要决定这个粒度； ② 每个 OS 单独一个 profile，因为同一条 passcode 策略在 iOS 与 macOS 上语义不同； ③ 用 Description 记"谁改的 + 改了什么"当版本控制（p.721）。 这三条都是"半年后维护"成本，不是配置技巧。

面试怎么用：被问"你怎么组织 MDM 配置"， 答"按 OS 分 profile、按 tag 分作用域、用 Description 做变更追溯"， 比答"我在 Settings 里点了 Add Profile"高一个层次。

案例 7 · 一次推两张证书（EAP-TLS 的前置作业）

场景：要让设备用证书入网，先得把证书送到设备上。

前提：设备证书来自 Cisco ISE 的 Certificate Provisioning Portal； 第二张是 ISE CA 证书（Wi-Fi payload 要知道"该信任谁"）。 可推送的格式有 .cer .p12 .crt .pem 四种（p.722）。

动作：Settings → 打开已有 profile → + Add Settings → Certificate → 填 Name → 有密码则填 Password → Certificate > Choose File 逐个导入 → Save。 同一流程做两遍（p.722-724）。

现象：点 Save 之后证书详情（Subject/CN、有效期）才填出来—— 界面在保存前不显示元数据（p.724）。

坑：这一步没做，下一步 Wi-Fi payload 的 Trusted Certificates 下拉框会是空的， 你会以为界面有 bug，其实是信任锚还没下发（p.726）。

面试怎么用：这是"配置项之间的隐式依赖"最好的例子—— 两个页面看起来无关，实际前者是后者的数据源。排障时先查依赖，别先怀疑产品。

案例 8 · EAP-TLS 零交互入网（全章最完整的实验，四层验证）

场景：公司要求员工连 Wi-Fi 不输密码、不点确认，且身份基于设备证书。

动作：Settings → profile → + Add Settings → Wi-Fi Settings； Configuration = Manual（默认）；填 SSID；勾 Auto Join； 勾 Disable MAC Address Randomization (iOS 14 or Later)； Security = WPA2 Enterprise（必须选含 Enterprise 的项，否则下面的 Enterprise Settings 不展开）； Protocols = TLS； Authentication > Identity Certificate 选案例 7 的设备证书； Trust > Trusted Certificates 勾 CN 为 ise.selab.local 的 ISE CA → Save（p.724-730）。

现象（分四层取证，这才是完整实验）： ① 配置层：图 11-18/11-19 显示两张证书的勾选结果（p.726）； ② 设备声明层：iPad 上 Settings > General > VPN & Device Management > Meraki Systems Manager， 在 WI-FI NETWORK 下能看到该 SSID 与所需证书（p.727）； ③ 体验层：全程零用户交互，直接连上（p.728）； ④ 后端证据层：Cisco ISE live logs 显示认证协议确实是 EAP-TLS（p.729）。

坑：连不上时先查 Meraki Dashboard 日志，再查 ISE 日志—— 这条链跨了三个系统（设备 / MDM / RADIUS），定位错系统是最大的时间浪费（p.728）。 另外"关闭 MAC 随机化"这个勾选很关键：否则每次连接 MAC 变化会让基于 MAC 的任何策略与日志失去意义。

面试怎么用：这四层验证是最有说服力的回答模板。 尤其第 ④ 层——"不是连上了就算成功，要去 ISE 日志确认协议真的是 EAP-TLS"， 说明你知道PEAP 也表现为能连上，只有日志能区分两者。

案例 9 · 用 VPN payload 下发公司 VPN（L2TP），并省掉重复输密码

场景：非 Meraki 的 VPN 服务器（或 Sentry 不适用的场景），用户不想手抄服务器地址与密钥。

动作：Settings → profile → + Add Settings → VPN Settings； Connection Name = Corp VPN；从另一个标签页的 IPsec Settings 页复制 Hostname 粘进 Server；复制 Shared Secret 粘进 Shared Secret； Connection Type = L2TP；可选勾 Send All Traffic（关掉 split tunneling）→ Save（p.730-734）。

现象：① iPad 的 MDM 详情页出现 VPN SETTINGS 下的 payload 名（p.731）； ② 用户被提示输入用户名密码后连上（p.732）； ③ 体验优化：Settings > General > VPN & Device Management > VPN 点蓝色 i → Edit → 填 Account / Password → Done， 之后不再重复输入（p.733）。

坑：连不上查 Dashboard 的 event log（p.732）。 另外记住边界：VPN payload 是给"非 Meraki VPN"用的；Meraki 自己的 Sentry VPN 只要几次点击， 不需要这套手工 payload（p.730）。同理 Wi-Fi payload 也是给非 Meraki SSID 或 Sentry 不兼容场景用的。

面试怎么用："什么时候用 Sentry，什么时候用 payload"是很好的辨析题： Sentry = 一键 + Meraki CA 自动发证 + 零交互；payload = 兼容存量非 Meraki 设备。 两条路并存不是重复功能，是迁移期的桥。

案例 10 · Passcode 策略：6 位 / 5 分钟 / 10 次，以及三种验证方法

场景：把 NIST AC-11（空闲锁屏）与 AC-7(2)（失败次数擦除）落成一条 payload。

动作：Settings → profile → + Add Settings → Passcode； Minimum Length = 6、Auto-Lock = 5 minutes、 Maximum Number of Failed Attempts = 10 → Save（p.735-738）。

现象（同一件事从三个层面取证）： ① iOS MDM 详情页 Contains: 里出现 Password Policy（p.737）； ② 点 Restrictions > Passcode，参数与 SM 完全一致（p.737）； ③ 最强证据：iOS Settings > Touch ID & Passcode 里 Erase Data 滑块变开启且灰化锁定——用户改不回去（p.738）。 Android 侧则是到 Settings > Security > Screen Lock 尝试改/删 PIN，应被拒（Android 10+，p.736）。

坑：看到 Contains: Password Policy 只能证明"描述文件里有这条"， 不能证明设备真的执行了。真正有效的验证是去系统设置里看那个开关的状态—— 灰化锁定 = 由 MDM 强制，这个细节在面试里非常加分。

面试怎么用："如何验证一条 MDM 策略真的生效"—— 答"三层取证：profile 声明 → 系统设置实际值 → 用户尝试修改被拒"。

案例 11 · 磁盘加密：故意不提供开关，这是设计而不是缺失

场景：合规要求"移动设备必须加密"，你要找那个开关。

动作：找了一圈发现SM 里没有"移动端磁盘加密"开关。 书上给的做法是只做验证：iOS 17.2+ 上 Settings > Face ID & Passcode 滚到最底， 最后一行显示 Data protection is enabled.；Android 侧只要确认已设 PIN 即可（p.738-739）。

现象：合规目标是达成了，但不是通过下发配置达成的。

坑 / 机制：iOS 的 data protection 与 Android 的 FBE 都是设了 passcode 就自动开启， 所以真正的杠杆是案例 10 的 passcode 策略。唯一的例外是 Mac：需要 FileVault 的 settings payload 去强制加密，再用 policy 审计合规（p.739）。

面试怎么用：这条很适合讲"控制目标 ↔ 控制手段"的分离： AC-19 要的是结果，SM 提供的是间接触发。 顺带说明为什么 macOS 要单独处理——桌面系统不会因为设了登录密码就自动全盘加密。

案例 12 · 用 Restrictions 隐藏 TikTok，以及一个破坏性的反向实验

场景：公司要求某些应用在设备上彻底不可见（不只是不能装）。

动作：Settings → profile → + Add Settings → Restrictions → 滚到 Apple Supervised Restrictions → Show or Hide Apps = Do Not Allow the Following Apps → Choose an App 输入 TikTok 选中 → 页面底部 Save（p.739-742）。

现象 1（正向）：profile 同步后该应用在设备上不可访问； iOS 的 SM profile 下会出现 Managed App 限制项作为凭证（p.741）。

现象 2（反例，本章最值得记住的破坏性行为）：在非 supervised 设备上做同样的操作， 结果所有非系统应用都被隐藏了（p.741）。 验证方法很朴素：直接在被影响的设备上搜那个应用名（p.741）。

坑：非 supervised 设备只能按 age rating 限制，不能点名隐藏（p.740）。 Apple Configurator 虽然能给设备开 supervision，但不适合大规模设备群（p.740）。

面试怎么用：这是"测试要覆盖失败路径"的真实案例—— 一个看起来只是"选个应用"的操作，在错误的注册方式下会一次性隐藏员工全部工作应用， 业务当场停摆。先在测试设备上验证 restriction 的实际效果，再推 Scope， 这条经验比任何一条配置项都值钱。

案例 13 · 推 Cisco Secure Client，并观察合规状态自动回归（全章闭环）

场景：案例 3 的策略把 Cisco Secure Client 列为必装应用， 所以一批设备此前一直显示"不合规"。现在要修复它们。

动作：Systems Manager > Apps（Monitor 下）→ + Add App → App Platform = iOS → 来源 App Store App → Next → 搜索选中 Cisco Secure Client（可选下载国家 App Store）→ 勾 Keep App Up to Date、勾 Remove with MDM、取消勾 Removable → Purchase Method 选 VPP 类以静默安装 → Scope = All Devices → Save → 回 Apps List 勾选该 app → Push > Push to All in Scope → Confirm（p.742-748）。

现象 1：若未设 Purchase Method，用户会收到安装通知、可以取消， 但 SM 会自动重试；设了则静默安装，图标直接出现在桌面（p.747）。

现象 2：iOS MDM 详情页点 Apps 可列出已推送的应用，确认安装成功（p.747）。

现象 3（闭环证据）：Devices 列表里这台设备从"不合规"变回"合规"（p.748）。 附注：图标显示的是 AnyConnect 而不是 Cisco Secure Client，因为品牌更名还在进行中（p.747）。

坑：三个开关的语义要弄清： Keep App Up to Date = 自动更新；Remove with MDM = 设备退出管理时一并卸载； 取消 Removable = 用户不能自行卸载（对应 PCI DSS 4.0 1.5.1「控制不可被用户更改」）。 这也是书里说的四项应用管理要求（p.742）：装检测类应用（CSF DE.CM-03）、防用户改动（PCI 1.5.1）、 能移除 EOL 软件、能禁止安装 EOL 软件（Essential Eight）。

面试怎么用：把这条案例当成"安全运营闭环"的完整叙事： 策略定义标准 → 报告发现差距 → 推送修复 → 报告复核通过。 很多人只会配策略，讲不出闭环，这四步正好补上。

案例 14 · 用 Duo Trusted Endpoints 替代设备证书

场景：不想维护一套 PKI 给每台设备发证，但仍要按设备可信度决定放行/拒绝。

动作：SM 在这里干三件事（p.748）： ① 推 Duo Mobile / Duo Desktop 应用； ② 用 payload 下发 Duo 应用的 Trusted Endpoints configuration key 与 Trusted Endpoints identifier； ③ 通过 API 集成把 SM 的资产清单数据提供给 Duo。

现象：Duo 能判定设备是否可信，管理员据此允许或拒绝访问——这是设备证书方案的功能替代品。

坑：它和案例 8 是两条不同的信任路线： 证书路线把信任放进设备（离线可验证、与 RADIUS 天然配合）； Duo 路线把判断放到云侧（依赖实时在线与 API 数据新鲜度）。 选型时要问"断网时还要不要验证"。

面试怎么用： "设备信任可以由三种东西证明：设备证书、MDM 清单、Duo 的 Trusted Endpoints"—— 能列出三条路线并说清各自的依赖，就是架构视角。

案例 15 · 推 OS 更新，与"最多推迟 3 次"这条硬限制

场景：合规报表显示大量设备版本落后，想批量升级。

前提：iOS 设备必须通过 ADE 注册且为 supervised（p.748）。

动作：Systems Manager > Devices（Monitor 下）→ 勾选设备 → Command = Install Available OS Updates → 右侧面板选 OS Version、 Install Action 保持默认 → Update → 点表格右侧齿轮加 OS Update Status 列 → 刷新看进度（p.749-750）。

现象：用户收到"组织要求升级"提示，最多推迟 3 次，之后必须升级才能继续用设备（p.750）。

坑：iOS 的更新是两步流程——先下载，再（重复执行一次命令）触发安装， 不是一键完成（p.749-750）。这解释了"命令发了却没升级"的常见疑惑。

面试怎么用：补丁管理最常见的反对意见是"影响业务"。 "可推迟 3 次"是把可用性让步写进产品的典型设计——既给用户缓冲，又保证收敛。 配合前面案例 5 的报表，就是一条完整的补丁治理链路。

案例 16 · 混合网络迁移：旧网 + 新网并存，用户不需要二次 onboard

场景：存量站点跑旧设备，新站点用 Meraki；而新网要上的 Sentry 特性 （如 WPA3、AnyConnect 场景）当前与旧设备不兼容（p.722、p.723）。

动作：新网络先启用 Sentry 系访问控制；同时用 SM 给用户设备下发旧网络的 profile（Wi-Fi / VPN / 证书）。

现象：用户继续连旧网完全不受影响；站点逐个升级后自然迁移到新网， 不需要重新注册或重新发证。

坑：这是一条设计层面的迁移策略，不是某个开关。 要点是让设备同时持有两套入网凭据——SM 同时是"新世界的入口"和"旧世界的兼容层"。

面试怎么用：被问"如何在不中断业务的前提下换架构"， 这就是标准解法：控制面先双轨、数据面按站点切换。 现实中大部分安全改造失败，不是因为技术不行，而是因为要求用户重新配置。

案例 17 · 反面案例：入网流程太麻烦，用户就会绕开你

场景：传统证书入网要用户自己下载描述文件、手动装证书、输账号——每步都可能卡住。

现象（书里点明的后果）：用户会去找开放 SSID， 或者自己插一个家用路由器（p.722）。安全控制不但没生效，还多了一堆看不见的资产。

对照解：Sentry + SM 的组合把这条流程压成"设备自己做"： Meraki 自有 CA 自动发证、SM 自动推证书与 Wi-Fi payload、用户零交互连上（p.722、p.724-730）。

面试怎么用：这是全书最"人"的一段，也是最容易讲出彩的： 安全控制的有效性 = 控制强度 × 用户遵守率。 再强的认证，如果用户都绕过去，等于零；而提升遵守率最有效的手段是把正确路径做成最省事的那条。

五、面试问答

Q1：Systems Manager 和 Duo 都要买吗？它们重叠吗？

一句话：不重叠，是 defense-in-depth： SM 管与报，Duo 拦与警（p.710-711）。

可展开：两者覆盖同一批属性（补丁版本、屏幕锁、磁盘加密、passcode）， 但作用方式相反：SM 是异步的管理面，改变设备的未来状态；Duo 是同步的准入面，判定当下能不能连。 只有 Duo → 不合规设备进不来，员工活儿干不了；只有 SM → 全靠自觉，没有强制力。 书里的典型配合是：SM 推补丁与配置，Duo 在设备落后时先提醒、再不达标就断网（p.748）。

Q2：为什么配了安全策略，设备还是不合规？

一句话：因为 Policies 只做审计，不下发任何设置或软件（p.716）。 策略定义"达标长什么样"，profile / app 才是达成它的手段。

可展开：所以操作顺序应该是先 policy 后 profile： 先有度量标准，才能用同一张报表证明修复有效。 本章的完整闭环是案例 13：策略发现缺 Cisco Secure Client → 推送该应用 → Devices 列表自动回归合规（p.748）。 这也是"只读层 / 可写层"这套分层存在的意义。

Q3：MDM 下一条命令，设备多久能收到？为什么不实时？

一句话：因为它不是长连接：APNS 先发静默通知 → 设备被唤醒后向 Dashboard check-in → 取回待执行命令（p.711）。所以是最终一致，不是实时。

可展开：推论有三条：命令会排队，设备离线时等上线再补； Apple 侧整条链路依赖 Dashboard 里那张 push 证书，过期 = 所有 Apple 设备失联； 证书申请时 Apple ID 必须开两步验证（p.712）。 面试里补一句"所以我把证书到期做成运维日历项"会显得真的运维过。

Q4：EAP-TLS 为什么能做到用户零交互？需要几张证书？

一句话：因为双向都用证书、不需要输密码，没有交互可做。 需要两张：设备证书（Identity Certificate）+ ISE CA 证书（Trusted Certificates）（p.724-730）。

可展开：两张证书解决的是相反的问题—— 前者证明"我是谁"，后者让设备判断"对面那个 RADIUS 是不是真的"。 对比 Ch7 的 PEAP：只验服务端、客户端交密码，是单向信任。 现场验证要走四层：profile 声明 → 设备 MDM 详情页 → 零交互连上 → ISE live logs 确认协议是 EAP-TLS（最后一步才是硬证据）。

Q5：为什么企业坚持用 ADE 而不是让员工手动装描述文件？

一句话：因为能力上限由注册方式决定： 只有 ADE 注册 + supervised 才能按名字隐藏指定 App、才能推 OS 更新（p.739、p.748）。

可展开：代价是 ADE 手动加入需要恢复出厂，因此不适用 BYOD（p.715）。 所以正确做法是按设备归属分池：公司资产 ADE + supervised；个人设备走 BYOD， Android 用 managed profile mode 把工作数据容器化。 最反直觉的一点是：在非 supervised 设备上做"隐藏某个 App"，会把所有非系统应用都隐藏掉（p.741）。

Q6：没有 MDM 的手机，你怎么证明它加密了？

一句话：移动端加密是设了 passcode 就自动开启的， 所以真正要管的不是"开加密"，而是强制 passcode（p.738-739）。

可展开：iOS 17.2+ 可在 Face ID & Passcode 底部看到 Data protection is enabled.；Android 设了 PIN 即是 FBE。 唯一要单独处理的是 macOS —— 需要 FileVault payload 强制加密，再用 policy 审计。 对照标准：这就是 AC-19 的要求，控制目标与实现手段是分离的。

Q7：怎么证明一条 MDM 策略真的生效了，而不是只写进了描述文件？

一句话：三层取证——profile 声明 → 系统设置里的实际值 → 用户尝试修改被拒（p.735-738）。

可展开：以 passcode 6 位 / 5 分钟 / 10 次失败为例： ① MDM 详情页 Contains: 出现 Password Policy； ② 点进 Restrictions > Passcode 参数一致； ③ iOS Touch ID & Passcode 里 Erase Data 滑块开启且灰化。 只有第三层能证明"由 MDM 强制、用户改不回去"。这条正好对应 PCI DSS 4.0 1.5.1「控制不可被用户更改」。

Q8：应用管理要满足哪些合规要求？SM 怎么覆盖？

一句话：书里列了四条（p.742）： 装检测类应用（NIST CSF 2.0 DE.CM-03）、 用户不可更改这些控制（PCI DSS 4.0 1.5.1）、 能移除 EOL 软件、能阻止安装 EOL 软件（Essential Eight）。

可展开：对应开关是： 推 Cisco Secure Client 带来 HIPS / NetFlow / 反恶意软件； 取消勾 Removable + Remove with MDM 实现不可卸载、退出管理时清理； Application Block List 与 Restrictions 覆盖禁装 EOL 软件。 注意 CSF 引用的是 v1.1 的 DE.CM-3，正文写的是 2.0 的 DE.CM-03，面试时按 2.0 说更稳。

Q9：让你给一家 500 人的公司设计端点上安全，你的顺序是什么？

一句话： 先分层（谁能被管到什么程度）→ 再定基线（policy）→ 再选修复手段（profile / app）→ 最后接准入（Duo）闭环。

可展开： ① 资产分池：公司设备走 ADE + supervised（拿到推 OS 更新、隐藏应用的能力）， BYOD 走 managed profile mode（不碰个人数据）； ② 打通 Apple push 证书并把到期做成日历项； ③ 用一条 Corp_Security_Policy 定义基线：passcode、未越狱、禁装名单、必装 Secure Client、 最低 OS 版本、30 天 check-in；开日报并确认收件人真的能收到； ④ 建 profile：passcode payload、证书 payload、Wi-Fi payload（EAP-TLS）； ⑤ 推应用与 OS 更新，观察合规自动回归； ⑥ 最后把 Duo Trusted Endpoints 接上，让不合规设备在连接层就被拦。 这套顺序的每一步都有可验证的输出，不是"功能清单"。

本章主线，一句话： MDM 的价值不在"能配多少"，而在"能证明并修复"。 策略是传感器（只读），profile 与 app 是执行器（可写），准入（Duo）是保险丝。 三者叠起来才叫闭环：看得见 → 修得好 → 进不来。 面试里只要按这个顺序讲，就不会掉进"背配置项"的坑。
