第 10 章 · 深度精读

流量安全与 SASE：两条检查链，一个顺序问题

这一章是全书篇幅第二大、也是控制措施最集中的地方。 表面上是「开了哪些功能」，实质上是一个顺序问题： 流量在什么位置、被哪一层、按什么依据判定，以及为什么这个顺序不能乱。

技术密度：极高 篇幅：119 页 面试高频：执行顺序 / IPS / SASE
i

标注约定：（p.xx） 为书中原文位置；（推论） 为机制推演。 本章实验多，我把它们压缩成「动作 → 验证现象 → 页码」的形式，方便直接复现。

一、设计理念：两条链，两种检查位置

书里实际上给了两套检查体系，很多人把它们混着讲，导致说不清「到底在哪一层被拦」。

体系执行位置执行顺序依据
MX 本地检查链 本地 MX 上，流量穿越设备时 L3（stateful，先匹配）→ L7 / NBAR（stateless，再评估）→ 内容过滤（URL / 类别 / Talos 威胁类别）→ AMP（文件 disposition）与 IDS/IPS（Snort 签名） p.594、p.597、p.603、p.610、p.614
Secure Connect 云链 Umbrella / SASE 云侧 DNS → Cloud Firewall → SWG → CASB → DLP p.617、p.696

1.1 为什么 DNS 排在最前面

书里对 DNS 安全的表述是「在任何其他连接建立之前检查 DNS 请求」（p.639-641）。 默认阻断被 Talos 判定为 host malware、command-and-control 基础设施、phishing 的域名， 还可以加选 Newly Seen Domains（常用于零日利用）。

（推论）这个位置的优势是「不用解密就能判断意图，且判定发生在 TCP 握手之前」—— 连接都还没建立，恶意软件拿不到任何载荷。这也是 SASE 体系里 DNS 层不可替代的原因： 后面每一层（SWG、CASB、DLP）都需要先有会话、甚至需要解密才能工作。

!

书中特别提醒：不建议删掉默认的阻断项（p.639-641）。 默认规则覆盖的是已被确认的恶意基础设施，删掉等于主动放行已知威胁。

1.2 HTTPS 是整条链的硬边界

这是本章最容易被误解的一点（p.598-599、p.636）： MX 对 HTTPS 站点的拦截只是 reset 连接——既看不到内容，也给不了用户 block page。 想真正看到内容，必须依赖 Secure Connect 的 HTTPS inspection + 客户端 Root CA。

换句话说，「开了内容过滤」和「能看到 HTTPS 内容」是两件事。 前者按域名/类别做判定（能拦但要重置连接），后者才是解密后按内容判定（能拦且能给提示页）。

1.3 为什么还要有 Cloud Firewall 这一层

云链里的 Cloud Firewall 提供的是与本地 L3 防火墙同类的规则能力， 但它有明确的体验缺陷（p.648）：只阻断，不给友好页面， 用户看到的是「page cannot be displayed」。官方建议网站类拦截改用 web policy，因为后者有 block page。

（推论）这暗示了功能分层：Cloud Firewall 适合协议/IP 级的策略 （拦 ICMP、拦某段地址），web policy / SWG 适合网站级的策略。 用错层不会失效，但会制造大量「打了电话才发现被拦」的工单。

1.4 SASE 相比本地设备到底解决什么

书里在总结处点了四个能力（p.617、p.706）： HTTPS 全解密、DNS 层前置拦截、 CASB / DLP 的数据外泄控制、集中策略。 附带效果是可以替代多个本地盒子，让站点部署更小的设备。

这四点是互相支撑的：DNS 管「去向」、解密管「内容可见」、CASB/DLP 管「数据出去」、集中策略管「一致执行」。 少任何一环，链条都会断在某个具体场景上。

二、机制拆解

2.1 L3 与 L7 的匹配顺序，以及一条被忽略的边界

MX 上的顺序是明确的（p.594、p.597）：L3 防火墙（stateful）先匹配，L7 / NBAR（stateless）再评估。 注意这里的状态差别——L3 是有状态的，L7 是无状态的；而组策略与无线防火墙里的 L3/L7 都是 stateless。

!

规则管不到自己（p.593-594）： 防火墙规则只作用于穿越设备的流量；源或目的为设备自身的流量不受这些规则约束。 另外，system 级 L7 与 L3 规则的处理顺序在 MX 与 MR 上不同，不能照搬。

2.2 L7 识别：NBAR 与 Geo-IP

L7 规则可以按应用（NBAR 应用库）、内容类别、hostname 等维度匹配。 Geo-IP 规则则依赖地理位置数据库——书里的实验是先到 MaxMind demo 确认某个域名解析到的 IP 归属地， 再配国家规则（p.600-603）。这个习惯值得学： 先查 IP 归属，再写规则，能避免「以为拦的是某个国家，实际拦的是 CDN 节点」。

2.3 内容过滤的判定依据

三个层次：Blocked URL List（精确域名）、Content Categories（内容类别）、 Threat Categories（Talos 威胁分类，例如 Malware Sites）（p.604-609）。

书里的实验流程体现了一个方法论：先用 Talos Reputation Center 查明目标域名的分类 （例如查出 adforce.com 属 Advertisements），再去配对应类别。 先确认分类，再配规则——否则你封的类别和你想封的东西可能不是一回事。

2.4 IDS/IPS：同一个引擎，两种模式

书里的定性很干脆（p.614-615）：IDS 与 IPS 是同一引擎的两种 Mode， Detection 只告警、Prevention 阻断。 规则覆盖面由 Ruleset 的 CVSS 阈值决定：

RulesetCVSS 阈值含义
Connectivity= 10只覆盖最严重的（可用性类）
Balanced≥ 9默认值
Security≥ 8覆盖最广，误报也最多
×

三个必须知道的覆盖边界（p.593、p.614、p.617）：

① 书中 Table 10-1 明确标注 MX 的 IDS/IPS 为 HTTP only；
② 同 VLAN 内主机之间的流量不被检查；
③ mTLS / QUIC 等不可检协议要靠 DNS 层策略来覆盖。

2.5 AMP：默认是关的，且有一个前置开关

这一点很多人搞错（p.610-611）：AMP 默认 disabled， 而且必须先在 Network-wide > General 启用 Traffic Analysis （Detailed: Collect Destination Hostnames）才能使用。

判定机制是云端文件信誉，给出三态 disposition： Clean / Malicious / Unknown。 已知 Malicious 的 HTTP 下载会被阻断。

书里强调的架构优势是：这套判定在云端完成，不牺牲设备吞吐（p.610-611）。 书中未展开 retrospective（事后追溯告警）的具体机制，这一层需要查 Cisco AMP 文档。

2.6 云端的两段式文件检查

到了 Secure Connect 侧，文件检查变成两段（p.671-674）： 先由 Cisco AMP 检查，再由 Umbrella 的 antivirus 引擎检查； 两段都完成后才交付文件，否则终止下载并显示 block page。

还可以再加一层 Secure Malware Analytics（Threat Grid）沙箱。 但有一个不可逆的配置点：区域（北美 / 欧洲）选定后不可更改—— 这涉及数据驻留合规，选之前必须和法务确认。

2.7 文件类型控制：改扩展名也没用

File Type Control 靠的是 Umbrella 的内部检测引擎判定真实文件类型， 所以即使被改了扩展名也能拦住（p.682）。 两个使用条件：只能在 Web policy 中启用，且依赖 HTTPS inspection。

2.8 SWG 的 destination list 有硬上限

书里给了具体数字（p.657-664）：新建 destination list 时类型选 Web Policy， 单表最多 5,000 条，但建议少于 100 条。 在 Default Web Policy 加规则后必须点 ENABLE RULE； HTTPS 场景要在 HTTPS Inspection 里选 Display Block Page Over HTTPS， 否则用户看不到提示页。

「上限 5,000、建议 100」这组数字反映的是匹配性能的现实约束—— 列表越长，每包匹配成本越高。这也是为什么大型组织要按业务线拆多个 policy 而不是堆一张大表。

2.9 HTTPS 解密与一条合规红线

HTTPS inspection 是 DLP、File Type Control、内容级判定能成立的前提。 但书里明确画了一条红线（p.675-676）： 受监管的敏感数据（例如 HIPAA 下的 PHI）应通过 Selective Decryption List 排除在解密之外。

这一点在面试里很加分：它说明「解密一切」不是正确答案， 解密范围本身就是一个合规决策，需要按数据分类划定边界。

2.10 CASB：先看清，再控制

书里把 CASB 拆成两个能力层次（p.688-690）：

  • App Discovery——报告在用哪些 SaaS / PaaS / IaaS，按类别与风险画像呈现（影子 IT 发现）
  • 功能级控制——对具体应用的具体操作做限制： 允许访问 Google Drive 但不允许上传；允许访问社交媒体但不允许 post / share

这个「按功能而非按应用」的粒度是关键：传统 URL 过滤只能整站放行或整站封禁， 而真正需要管的是「能看不能发」这类场景。

2.11 DLP：三种机制覆盖三条外泄路径

机制覆盖路径作用
Real-Time RulesWeb 流量与 Web 表单实时扫描并阻止外泄（含粘贴进网页表单的内容）
SaaS API RulesOffice 365 等云服务把策略延伸到云端，核查外部文件共享是否符合数据分级
Discovery Scan外部存储位置扫描并报告是否合规（发现了什么、在哪）

依据：p.696

数据判定方面（p.697-700）：开箱即可识别 GDPR、HIPAA、PII、PCI 数据， 可用内置 PCI Classification 或自定义 Data Classification； 可搜「Content and File Name」，也可用 File Labels 读文档元数据 （Office 属性 / 敏感度标签、PDF 属性）。

前提仍然是必须有 HTTPS inspection 才能生效—— 这条依赖关系把整章的线索串起来了：没有解密，就没有内容级控制。

2.12 Secure Connect 的两种接入方式，差别在流量路径

接入方式机制验证方式
DNS 接入 DHCP 把 208.67.222.222 与 208.67.220.220 下发给客户端（Use Umbrella） 访问 welcome.umbrella.com
隧道接入 MX 把 Secure Connect 当作一个普通 Auto VPN hub 来建连；spoke 站点自动获得默认路由，hub 站点可配置 DLP 策略里的 identity 以 Tunnels 形式出现

依据：p.630-631、p.635、p.700

这个设计的巧妙之处是复用 Auto VPN：不用为 SASE 单独建一套 IPsec（p.533）。 书里也点明，改用 Secure Connect 后「连 SASE」不再是必须配 non-Meraki IPsec peer 的场景。

五、面试问答

Q1：MX 上的流量按什么顺序被检查？

一句话：L3（stateful）先匹配 → L7 / NBAR（stateless）再评估 → 内容过滤（URL / 类别 / Talos 威胁类别）→ AMP 与 IDS/IPS（p.594、p.597、p.603、p.610、p.614）。

可展开：L3 有状态而 L7 无状态； 组策略与无线防火墙里的 L3/L7 都是 stateless，所以 deny 后要显式放行回程； 规则只作用于穿越设备的流量，设备自身发起的流量不受约束。

Q2：为什么 SASE 的执行顺序是 DNS → Cloud Firewall → SWG → CASB → DLP？

一句话：越前面越便宜、越不需要解密——DNS 能在连接建立之前就判定去向， 越靠后的层（SWG / CASB / DLP）需要的上下文越多，DLP 甚至必须有解密才能看内容（p.617、p.639、p.696）。

可展开：DNS 层覆盖 mTLS / QUIC 等不可检协议； 解密是内容级能力的前置条件；解密范围本身要按合规要求划定（HIPAA PHI 应排除）。 回答时讲清「成本递增」与「上下文递增」两条主线即可。

Q3：IDS 和 IPS 的区别？该选哪个 Ruleset？

一句话：同一引擎两种 Mode——Detection 告警、Prevention 阻断； Ruleset 按 CVSS 阈值分 Connectivity(=10)、Balanced(≥9，默认)、Security(≥8)（p.614-615）。

可展开：阈值越低覆盖越广、误报越多，所以这是可用性与检出率的权衡； 另外要知道覆盖边界——HTTP only、不检查同 VLAN 内主机互访、不可检 mTLS/QUIC。

Q4：一个恶意文件是怎么被拦住的？

一句话：AMP 用云端文件信誉给出 Clean / Malicious / Unknown 三态判定， 已知 Malicious 的 HTTP 下载直接阻断；云端判定不占用设备吞吐（p.610-613）。

可展开：前提是启用 Traffic Analysis；告警在 Security Center > MX Events； 云侧还能做两段式检查（AMP + Umbrella antivirus）甚至 Threat Grid 沙箱， 两段都完成才交付文件。Unknown 文件靠沙箱与 retrospection 补位。

Q5：内容过滤能看 HTTPS 内容吗？

一句话：不能。MX 对 HTTPS 只 reset 连接，既无内容可见也无 block page； 要看到内容必须走 Secure Connect 的 HTTPS inspection + 客户端 Root CA（p.598-599、p.636）。

可展开：所以「开了内容过滤」只等于按域名/类别拦截； 真正的按内容判定（DLP、文件类型、CASB 功能控制）都依赖解密。 反过来，解密范围要按数据合规边界设置（Selective Decryption List 排除 PHI）。

Q6：SASE 相比一堆本地安全盒子，优势在哪？

一句话：四个本地设备拿不到的能力——HTTPS 全解密、DNS 层前置拦截、 CASB/DLP 的数据外泄控制、集中一致的策略（p.617、p.706）。

可展开：附带收益是站点可以只放小设备，减少本地硬件的运维与容量规划负担； 代价是流量要引到云（隧道或 DNS 方式），对链路质量和云侧可用性有依赖。 回答时把「能力增量」和「依赖代价」一起说，会比单方面夸更有说服力。

i

本章的主线，一句话： 位置决定能力，解密决定深度。 DNS 层能拦在建连之前但看不到内容；本地 MX 能在 L3/L7 精确命中但拿 HTTPS 没办法； 云端 SASE 能解密看内容但要承担流量绕行与合规边界的代价。 任何一道防线说清楚「它在哪、看到什么、拦得住什么」，就是合格的回答。
