WAN 与 Auto VPN：零配置背后的控制面

Auto VPN 是 Meraki 最有辨识度的能力，也是最容易被误解的—— 很多人以为「流量会绕经 Dashboard」，实际上云端只做注册与密钥下发， 数据面是 MX 之间直连的。理解这条分界线，才能理解它的性能与限制来自哪里。

i

标注约定：（p.xx） 为书中原文位置；（推论） 为机制推演。 本章有几处常见说法书里确实没写——比如 SD-WAN 的 uplink selection 探测细节、 与传统 DMVPN/MPLS 的系统对比，我不会虚构，遇到会明确标注。

一、设计理念：控制面在云，数据面在设备

书里对 Auto VPN 的机制描述得很克制，但足够看清设计（p.528）： Dashboard / VPN Registry 只做三件事——注册、下发对端信息、下发「双向各一个 16 字符密钥」 （走 NexTunnel / TCP 443）。隧道随后由 MX 之间直接建立，并自动传播路由。

正因如此，管理员的动作被压缩到两步：选 VPN 类型 + 勾需要通告的子网。 这是「零配置」的全部含义。

◆

（推论）这条分界线决定了三件事： ① 数据面不经过云端，所以隧道带宽不消耗云的转发能力，也不受 Dashboard 可用性影响（已建隧道可继续转发）； ② 但新建隧道、配置变更、路由更新依赖云端，Dashboard 不可用期间无法新增站点； ③ 密钥由云端协商下发，意味着云账户的安全等级等于全网 VPN 的安全等级—— 这也是为什么第 3、5 章要把 Dashboard 管理员访问管得那么死。

1.1 拓扑取舍：先把流量走法想清楚

拓扑隧道数量流量走法适用判断
hub-and-spoke 最少 spoke 只连 hub，spoke 之间流量过 hub 分支之间几乎不通信；或规模大到要控制隧道数（p.528）
full mesh（多 hub） 随站点数平方增长 hub 之间自动 full mesh 分支之间流量大，绕 hub 会浪费带宽与增加延迟（p.528）
专用 MX 作 hub（VPN Concentrator mode） 最少 集中在数据中心做汇聚 规模优先，接受中心化转发（p.528）

书里的演进逻辑很清楚：分支间流量大了，就把分支也设为 hub，一路演进到 full mesh； 反过来，规模优先就用专用 MX 做汇聚，隧道数最少（p.528）。 这是一个可以逐步调整的决策，不需要一开始就定死。

1.2 一条重要的产品哲学分界

同样是「建一条 IPsec 隧道」，Meraki 内部与对外是两套完全不同的设计：

对比项Auto VPN（双方都是 Meraki）non-Meraki VPN peer（对方是第三方）
认证云端协商下发密钥只支持 preshared key，不支持证书（p.533）
双 WANprimary 与 secondary 上同时自动建隧道（p.537）只用 primary Internet uplink，官方称增强功能还在规划（p.537）
密钥管理每对隧道独立协商organization-wide，多台 MX 共用同一个 shared secret（p.533）
配置成本选类型 + 勾子网手填 Public IP/FQDN、secret、私网段、IPsec policy

这个对比说明 Meraki 的取舍：「自己人之间」的隧道做到极致自动化， 「跟外人」的连接降级为传统 IPsec peer。 报障时如果对方说「我们也是 Meraki」，那大概率不是配置问题而是组织归属/子网通告问题； 如果对方是第三方设备，就要按传统 IPsec 的思路查（PSK、UDP 500/4500 可达、仅 primary）。

从参数就能看出两者的定位：Client VPN 用的是 3DES + SHA1 这种明显偏旧的组合， 但胜在零成本、零客户端安装（系统自带）；AnyConnect 是 AES-256 + TLS/DTLS， 支持 SAML 与按域名分流，代价是要额外许可。 书里推荐用 AnyConnect（p.541）。

1.4 vMX：把 Auto VPN 的边界推到云上

vMX 的定位是把 Meraki 的安全栈放进 AWS/Azure 的 VPC，让云上资源也成为 Auto VPN 的一个站点（p.566-586）。 但它的能力边界非常明显——这是一台「为组网而生」的虚拟设备，不是完整功能的 MX： 不支持 AMP、IDS/IPS、Geo IP L7 规则、802.1X 端口认证、Splash page、双 WAN 或 LAN 口（p.563）。

换句话说，云上那一段的流量安全检查是缺失的。如果架构上依赖 vMX 做安全出口，这个坑必须在设计阶段就补掉。

二、机制拆解

2.1 双 WAN 的行为差异，决定了故障切换能力

书里给了两条硬事实（p.537）：

  • Auto VPN 会在 primary 与 secondary WAN 接口上同时自动建立隧道——所以一条上行挂了，隧道不需要重建，切换是「换个口继续走」
  • non-Meraki VPN 连接只用 primary Internet uplink——primary 挂掉，这条隧道就没了，官方称增强功能「尚在规划中」

再叠加 HA pair 的 automatic failover（p.528），构成两级冗余： 单条上行故障靠双 WAN 隧道，整台设备故障靠 HA pair。

可观测性上，在 VPN Status 页把鼠标悬停在网络名上，可以看到该隧道的 latency 与 usage（p.531）——这是判断「隧道活着但质量差」的唯一入口， 比只看 up/down 有用得多。

2.2 non-Meraki peer 的配置结构与一个方向性陷阱

配置路径是 Organization-wide > Non-Meraki VPN Peers > Add a Peer（p.534-538）： Type 选 Hub (Mesh)、填 Public IP/FQDN、Shared Secret、Private Subnets、 Availability（保持 All Networks 或用 Tags 限定），然后选 Preset 或自定义 IPSec Policy。

如果子网填 0.0.0.0/0，会弹窗提示最长匹配优先，需要手动 Confirm。 这个提示很关键——它意味着默认路由不会覆盖更具体的路由，但会与同精度的路由竞争。

!

方向性陷阱（p.538）：site-to-site VPN 的防火墙规则是 outbound 且 organization-wide 的。要拒绝到某个子网的流量， 必须把该子网写到 Source（实际效果是阻断回程流量）； 如果只想对某些远端站点生效，就把该站点的本地网段写进 Destination。

规则方向与直觉相反，是这类配置最常见的翻车点。

2.3 Client VPN 的关键参数

路径：Security & SD-WAN > Client VPN 的 IPsec Settings（p.542-547）。要点：

  • Hostname 由 Meraki 动态 DNS 自动生成，解析自动更新——不需要自己有公网域名
  • Subnet 必须未被占用，配置前先到 Route Table 查一遍
  • DNS Server 可选 Use Umbrella 或 Specify Nameservers——这是把远程接入流量导向 Umbrella 的开关
  • Shared Secret 建议不要首尾使用特殊字符——系统自带客户端对特殊字符的兼容性差
  • Authentication 选 RADIUS 是推荐项，Meraki Cloud Authentication 只适合小规模

2.4 AnyConnect 的关键参数

（p.552-556）

  • 端口默认 443，且不能与 NAT exceptions（No NAT）功能启用在同一 WAN uplink 上
  • 不支持 cellular 接口——若必须经蜂窝建 VPN，官方建议加 Meraki MG cellular gateway 并用 IP Passthrough 模式
  • 平台固件门槛：≥16.16（含 vMX）；但 MX64(W)/MX65(W) 需 ≥17.6；IPv6 Prefix 需 ≥18.104
  • Client Routing 即传统 split tunneling；Dynamic Client Routing 可按域名（而非子网）决定流量进出隧道，让云服务直连
  • Session Timeout 默认 None，Custom 最长 256 小时
  • 443 若被其他 Web 服务占用，建议把 VPN 用户终结到另一台 MX

部署主干（p.566-586）：Dashboard 建 Security Appliance 网络并选 vMX license → Generate Authentication Token（1 小时内必须用） → AWS 建 Internet Gateway + 0.0.0.0/0 默认路由 → Marketplace 订阅 vMX，Advanced Details 里设 Metadata Accessible=Enabled、Metadata Version=V1 and V2 (Token Optional)、 Hop Limit=1，User Data 粘入 token → 关掉网卡 Source/Destination Check，否则转发不生效。

三、书中的实验

3.1 hub + spoke：三步配完，三步验证

配置（p.529-530）：

  1. Hub 站点 Type 选 Hub (Mesh)（exit hub 不需要；exit hub 用于 full-mesh 下当默认网关，文档中称 full-tunneling）
  2. 对需要通告的子网启用 VPN Mode，Save
  3. Spoke 站点 Type 选 Spoke，Hubs 已自动选中可排序；若 hub 提供 Internet 访问则勾 IPv4 Default Route，启 VPN Mode，Save

验证（p.530-532）：

  • Security & SD-WAN > VPN Status 看隧道 Up，悬停看 latency / usage
  • Exported Subnets 看通告网段
  • Route Table 按 Destination 过滤，确认从 hub 收到的路由
  • Appliance Status > Tools > Ping 打 hub 侧网段网关

这四步的顺序值得记住：隧道 → 通告 → 路由 → 连通性。 排障时按这个顺序定位，能迅速区分「隧道没建起来」和「隧道通了但路由没学到」。

3.2 Client VPN 连通验证

配完后在 macOS System Settings > VPN 添加 L2TP over IPSec profile 并连接（p.542-547）。 这一步证明了 L2TP 方案的最大优势：系统自带客户端，无需安装任何软件。

3.3 Sentry VPN：零用户干预的连接

Client VPN > IPsec Settings 下方启用 Systems Manager Sentry VPN Security， Add Sentry Network 选含 Systems Manager 设备的网络、Scope 设 All Devices、勾 Send All Traffic（p.549-552）。

设备端在 Settings > General > VPN & Device Management > Meraki Systems Manager 里 滑动 VPN Status 即连接，无需任何用户干预。 想加速下发可在 Systems Manager > Devices 执行 Sync Profiles。

3.4 用 Group Policy 限制 VPN 用户能访问什么

这是本章一个很实用的例子（p.561-563）：在 AnyConnect Settings 的 Default Group Policy 应用策略 Remote_access_VPN_users，其中含一条阻止 ICMP 到 10.200.155.10 的 L3 防火墙规则。

结果：用户仍能 ping 网关 10.200.155.1，但 ping 不通 10.200.155.10—— 精准命中，不影响其他流量。

书里同时列出了其他可选手段：Client Routing、Filter-ID RADIUS 属性、 用 Sentry policy 分配 group policy、Outbound L3 firewall。 这说明「限制 VPN 用户访问范围」有多种实现路径，选哪种取决于策略从哪来（本地静态 / RADIUS 动态 / MDM 下发）。

五、面试问答

Q1：Auto VPN 是怎么做到「零配置」的？流量会经过 Meraki 云吗？

一句话：Dashboard / VPN Registry 只负责注册、下发对端信息和「双向各一个 16 字符密钥」（NexTunnel / TCP 443）， 隧道随后由 MX 之间直接建立并自动传播路由——数据面不绕云（p.528）。

可展开：所以管理员只选 VPN 类型 + 勾子网； 代价是新建隧道与配置变更依赖云端可用性，且云账户的安全等级等于全网 VPN 的安全等级 （这条是我基于机制的推论，回答时说明「推论」更稳）。

Q2：hub-and-spoke 还是 full mesh？

一句话：看分支之间的流量——绕 hub 浪费带宽就加 hub 直到 full mesh； 反过来规模优先就用专用 MX 作 hub（VPN Concentrator mode），隧道数最少（p.528）。

可展开：hub 之间会自动建立 full mesh； spoke 只连 hub 且 spoke 间流量过 hub；拓扑可以逐步演进，不必一次定死。 回答时补一句「隧道数随站点数平方增长」能体现对成本的考虑。

Q3：Auto VPN 和 non-Meraki peer 有什么本质区别？

一句话：三点差异——只认 PSK 不认证书、必须 UDP 500/4500 可达、只走 primary uplink； 而 Auto VPN 双 WAN 都建隧道并支持 HA pair 自动 failover（p.533、p.537）。

可展开：non-Meraki peer 是 organization-wide 的，多台 MX 共用同一 shared secret， 这既是便利也是风险（一台泄露等于全体泄露）。

Q4：Client VPN 和 AnyConnect 怎么选？

一句话：Client VPN 是 L2TP + 3DES/SHA1、任意 license 可用、无 split tunnel、可被 Sentry VPN 免配置推送； AnyConnect 是 TLS/DTLS + AES-256、支持 SAML 与按域名分流、需额外 licence（p.541）。

可展开：Cisco 推荐用 AnyConnect。 如果被问「为什么还留着 Client VPN」，答案是零成本 + 系统自带客户端 + 可配合 Sentry 做零干预接入。

Q5：为什么 vMX 不能替代本地 MX 做完整安全出口？

一句话：vMX 不支持 AMP、IDS/IPS、Geo IP L7 规则、802.1X 端口认证、双 WAN 与 LAN 口（p.563）—— 它的定位是组网，不是完整安全栈。

可展开：所以云上流量的安全检查要在架构上另找落点 （比如出云流量引到 Secure Connect 或本地 MX 做检查），不能默认「有 vMX 就有 IPS」。

Q6：VPN 隧道通了，但访问不了对端某个子网，怎么查？

一句话：按 隧道 → 通告 → 路由 → 连通性 四步走： VPN Status 是否 Up、Exported Subnets 是否通告了该网段、Route Table 是否学到、Tools > Ping 是否通（p.530-532）。

可展开：第四步不通时再检查 site-to-site 防火墙规则—— 注意它是 outbound 且 organization-wide，且要阻断某子网得写进 Source（p.538）。 如果是第三方对端，还要确认 UDP 500/4500 可达且只用了 primary uplink。

i

本章要记住的那条分界线： 控制面在云（注册、对端信息、密钥），数据面在设备（MX 之间直连）。 所有「零配置」的好处来自前者，所有「依赖云」的风险也来自前者； 所有性能优势来自后者，所有「加密参数不可调」的约束也来自后者。
