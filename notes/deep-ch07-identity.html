身份与认证：用户凭什么能进网络

这一章解决的不只是「怎么配一个 SSID」，而是四条认证路径的能力边界： Meraki Cloud Auth、AD 直连、RADIUS + ISE、SAML + Duo。 书里的结论很明确——企业环境别自己造轮子，把判断交给 ISE，把第二因素交给 Duo。

技术密度：极高 含书中实验全流程 面试高频：802.1X / PEAP / SAML
i

标注约定：标 （p.xx） 的是书中原文位置； 标 （推论） 的是我根据书中机制推出来、书里没有明说的内容，用来把链路补完整。 书中未涉及的部分我会直接写「书中未涉及」，不做补全式编造。

一、设计理念：为什么是这四条路

Meraki 在认证上的设计思路不是「给一个万能方案」，而是把认证拆成四个能力层级， 每层解决不同规模的问题，代价也逐层上升。理解这个阶梯，比记住某个 SSID 怎么点更有用。

方案解决什么覆盖范围关键代价书中定位
Meraki Cloud Authentication 管理员即用户，开箱可用 wired / wireless / VPN 各自独立配置 只能网络级配置；密码由管理员生成并以邮件明文发送；802.1X 用户无法自助改密 只适合家庭、小型企业或 lab；企业强烈建议换外部 IdP（p.290-291）
Active Directory 直连 复用已有域账号与组 仅 MX，不适用于 MS / MR 的 access policy 缺 ISE 的排障工具；证书配置对新手棘手；LDAP 不把客户端 IP 传给 Duo 「感觉只是为了支持传统遗留部署而存在」（p.289、p.373）
RADIUS + Cisco ISE 802.1X 准入、按身份授权、SGT 下发 wired / wireless / VPN 全接入方式 需维护 ISE；需 PKI（用 EAP-TLS 时）；organization-wide RADIUS 目前只支持 wired 企业标配，技术难度最高的需求必须上 ISE（p.290、p.326）
SAML + Duo 把认证委派给云 IdP，顺带拿到 MFA 仅 AnyConnect VPN；不支持 IPsec client VPN，不支持 802.1X 覆盖范围窄；RADIUS 路径没有 inline enrollment，用户要事先注册 需要同时满足 SAML 与 RADIUS 时，ISE 和 Duo 一起上（p.290、p.295）

1.1 为什么 SAML 只覆盖 AnyConnect VPN

这是最容易被误解的一点。直觉上「SAML 更现代，为什么不用它做 802.1X」， 但 SAML 断言解决的是「这个用户是谁」，而 802.1X 需要的远不止身份： 端口级的 Accept/Reject、授权结果下发（VLAN / SGT / ACL）、会话中途的 CoA 变更、 计费审计——这些是 RADIUS 协议族的职责，SAML 断言给不了。

所以 Meraki 的边界划得很清楚：SAML 管「人进 VPN」和「管理员进 Dashboard」， RADIUS 管「设备进端口/进 SSID」（p.295、p.346）。两者在同一个组织里并存，不是二选一。

1.2 为什么 ISE 是这套体系的「大脑」

书里给 ISE 的定位是 IAM / 策略引擎，具体承担三件事（p.290）：

  • MFA——作为 RADIUS 服务器串联 Duo，把第二因素塞进 802.1X 流程
  • 授权与策略下发——分配 SGT、ACL，决定认证通过后给什么权限
  • 充当 CA——签发客户端证书，这是 EAP-TLS 能落地的前提

反过来说，「按时间段限制访问」「限制并发登录」这类需求的技术难度最高， 只有 ISE 的授权策略引擎能做（p.290）。这就是为什么企业规模的答案不是「Meraki 自带功能再配一配」。

1.3 Duo 不只是 MFA

书里特别澄清了一个概念（p.290）：Duo 在 SAML 场景里之所以能当 IdP，是因为 Duo Single Sign-On 本身就是 cloud-hosted SAML 2.0 identity provider， MFA 只是它的一项能力。这一点决定了它才能支持 Duo inline enrollment—— 用户在首次登录流程里直接完成注册，而不是管理员事后发邮件批量导入。

!

同一个 Duo，两种接入方式的体验完全不同： SAML 路径有 inline enrollment；RADIUS 路径没有，用户必须事先注册—— 要么逐个点 Send Enrollment Email，要么用 Bulk Enroll Users 导入 CSV（p.289、p.362）。 这是选 SAML 而不是 RADIUS 做 VPN 的一个实际理由。

二、机制拆解：802.1X 在 Meraki 上实际怎么跑

2.1 三段链路，各段用什么协议

书里的链路是三段（p.325、p.341、p.343）： supplicant（客户端）→ Meraki MS/MR/MX（authenticator，ISE 眼里叫 NAD）→ 企业 RADIUS（ISE）→ AD。 客户端与 Meraki 设备之间跑的是 EAP（封装在 802.1X 的 EAPoL 帧里）， Meraki 设备与 ISE 之间把 EAP 载荷封进 RADIUS 报文。

Meraki 侧需要配的只有三项：RADIUS 服务器 IP/FQDN、Port 1812、shared secret（p.325）。 ISE 侧则要反过来把 Meraki 设备登记为 NAD（network access device）， 登记源 IP 或子网并配置同一个 shared secret，且 IPSEC 选项必须设为 No（p.315、p.317）。

◆

ISE 的 NAD 列表本质是一张白名单：只有登记过的设备发来的 RADIUS 请求才会被处理。 所以 802.1X「配了但不通」，第一件事不是看证书，而是看 ISE 里那台设备的源 IP 登记对不对。

2.2 关键细节：RADIUS 源 IP 取决于拓扑

这是本章最有工程价值的一条，也是面试里能立刻区分「配过」和「背过」的点（p.315-316）：

设备所处的拓扑发出的 RADIUS 源 IP
MS / MR 位于不参与 site-to-site VPN 的 MX 之后该 MX 的公网 IP
MS / MR 参与 site-to-site VPNMeraki 设备的本地 IP
MX 自身做 802.1X通常是它的 Internet 接口地址

（推论）这意味着同一个组织的不同站点，可能需要在 ISE 里登记成完全不同的地址形态： 未上 VPN 的分支登记 MX 公网出口，开了 VPN 的分支登记内网段。 一旦拓扑变更（比如后来加了 Auto VPN），原来登记的公网 IP 立刻失效，认证静默失败。

2.3 PEAP 与 EAP-TLS：差在「谁证证明谁」

书里的定性就一句话，但信息量很足（p.325）：PEAP 是单向信任（one-way trust）， ISE 用证书标识自己，客户端不需要证书； 而 EAP-TLS 同时使用客户端与服务器证书。

Cisco ISE 开箱即提供 PEAP 所需的服务器证书，这是它部署门槛低的直接原因（p.325）。 书中演示时，客户端侧只做了一件事：macOS 弹出 Verify Certificate 提示，点 Continue 接受 ISE 的证书（p.345）。

!

（推论）PEAP 的强度上限在哪：PEAP-MSCHAPv2 的内层只用 TLS 隧道保护用户名密码， 认证的本质仍然是「把域密码交出去验证」。也就是说， 能拿到用户密码的一方就能完成认证，服务器无法区分是不是本人在操作。 EAP-TLS 则要求客户端持有私钥，私钥不出设备、不可离线复制，这才是它更强的根本原因。

书中未涉及PEAP 与 EAP-TLS 的具体握手包序与算法协商过程——这一层需要查 RFC 与 ISE 文档。

2.4 ISE 的授权模型：默认就是拒绝

书中反复出现的一个细节：ISE 的默认授权策略是 deny， 所以建完 policy set 后必须显式插入授权规则才能放行—— 条件是 AD 的 ExternalGroups 属于 Network Access 组，Profile 设为 PermitAccess（p.336、p.338）。

这条规则的价值在于：「认证通过」不等于「授权通过」。 用户密码对了只是第一步，还得命中一条授权策略才会被放行。 这正好对应最小权限原则——默认 deny，按组授予。

2.5 Duo 接在哪里，决定你能用哪些能力

书里明确指出 Duo Authentication Proxy 部署在认证链的哪个位置「有讲究」， 不同位置会影响可支持的特性，例如 CoA（p.346）。

RADIUS + MFA 的串联方式（p.346、p.367-373）： Duo Authentication Proxy 接收 RADIUS 请求、查询 AD，并与 AD 同步用户与组； ISE 把 Duo 配成 External RADIUS Server， 再用 RADIUS Server Sequences 把 policy set 的 Allowed Protocols 与 Server Sequence 指向 Duo（Proxy Sequence）。

Duo failmode行为取舍
safe主认证成功即放行，不等 Duo 云保可用性，牺牲第二因素（p.349）
secureDuo Cloud 不可用时直接拒绝认证保安全，Duo 故障即全员登不上（p.349）

这是一个典型的安全 vs 可用性决策点，没有标准答案，取决于业务能否接受「认证服务故障 = 全员断网」。

2.6 SAML 里 Meraki 是 SP，不是 IdP

书中 AnyConnect 的 SAML 流程是标准 SP 视角（p.295-299）： 把 Duo 提供的 SAML Metadata XML 上传到 Dashboard， 同时在 Duo 里填写 AnyConnect Server URL。 也就是说 Meraki 信任 Duo 签发的断言，自己不做身份判定。

书中未涉及 IdP-initiated 与 SP-initiated 两种发起方式的差异。

三、书中的实验（可当实操脚本）

3.1 SAML + Duo + Entra：三个组件怎么分工

实验组成是 Meraki Dashboard 的 AnyConnect VPN + Cisco Duo（IdP 兼 MFA）+ Microsoft Entra（身份管理）（p.295-303）。步骤概括：

  1. 在 Entra 中另建 Network Access 组——把「能连 VPN 的人」从「全公司」收窄成一个组
  2. Duo 里 Protect meraki secure 应用，填入 AnyConnect Server URL
  3. 下载 Duo 的 SAML Metadata XML，上传到 Dashboard 的 AnyConnect 配置
  4. 在 Entra 的 Duo SSO 企业应用中分配该组，让组成员获得 SSO 资格

这四步的结构值得记住：身份源（Entra）决定谁有资格 → IdP（Duo）决定怎么验 → SP（Meraki）只负责信任。

3.2 无线 PEAP：不用客户端就能测

这是本章最实用的一个技巧（p.339-342）：无线 RADIUS 可以在 Dashboard 内直接测试， 不需要真实无线客户端。但有两个前提——SSID 必须具备 L2 连通性（AP 与交换机在同一 VLAN）， 且 Dashboard 会逐个检查每台 AP 到 RADIUS 服务器的可达性。

后一点很关键：它把「某台 AP 认证失败」这类问题提前暴露成「这台 AP 到 ISE 不通」， 把排障从「认证问题」降级成「连通性问题」。

3.3 有线 802.1X：一条完整的成功链路

书里用 MX 的 LAN 口做验证（并注明生产环境应改用 MS 交换机）（p.342-346）： Mac 侧用 iMazing 生成并推送 Profile，EAP Setup Modes = Login Window， Accepted EAP Types = PEAP。

实测流程是三步：弹登录框 → 接受 ISE 服务器证书 → Dashboard event log 依次出现 「端口接入」「EAP 认证完成」「放行入网」。 事件日志把这个过程拆成可观测的三段，这正是排查 802.1X 时应该看的东西。

3.4 VPN + RADIUS + Duo + AD 四件套

实验拓扑是 Meraki MX 的 AnyConnect VPN + Cisco ISE（RADIUS server）+ Cisco Duo（MFA）+ Microsoft AD（身份管理）， 书中注明与 AD 通信使用 LDAP（p.346-347）。

◆

驱动这套组合的现实原因：PCI DSS 从 3.2.1 升到 4.0 后， 要求所有远程访问都必须 MFA，不再只限于敏感区域（p.346）。 这条变化直接解释了为什么书里所有远程接入方案都默认带上 MFA。

五、面试问答：怎么把机制讲清楚

下面每个问题先给「一句话答案」，再给可以继续展开的支撑点。 一句话版本用来开场，支撑点用来接住追问。

Q1：802.1X 在 Meraki 上是怎么跑的？

一句话：客户端（supplicant）与交换机/AP（authenticator，ISE 眼中的 NAD）跑 EAP， authenticator 把凭据封进 RADIUS 送到 Cisco ISE，ISE 再回 AD 校验， 结果以 Accept/Reject 回给端口或 SSID（p.325）。

可展开：Meraki 侧只配 3 个参数（IP、1812、secret）； ISE 侧要把 Meraki 设备登记为 NAD 且 IPSEC=No； RADIUS 源 IP 随拓扑变化（VPN 内外不同）；ISE 默认 deny，认证通过后还要命中授权规则。

Q2：PEAP 和 EAP-TLS 怎么选？为什么 PEAP 被认为更弱？

一句话：PEAP 是单向信任，只有服务器用证书证明自己，客户端交用户名密码； EAP-TLS 是双向证书，客户端必须持有私钥（p.325）。

可展开：PEAP 部署门槛低（ISE 开箱带证书、客户端零配置）， 但强度等价于「谁能拿到域密码谁就能认证」； EAP-TLS 私钥不出设备，所以更强，代价是要 PKI——书里的做法是用 ISE 当 CA 签发， 再由 Systems Manager 自动下发证书和 profile（p.429-446），把 PKI 成本压到最低。

Q3：802.1X 配好了但不通，从哪查？

一句话：先确认 ISE 里登记的那台 NAD 的源 IP 和实际发出报文的源 IP 是否一致（p.315-316）。

可展开：源 IP 取决于 MS/MR 是否在参与 VPN 的 MX 后面（公网 IP vs 本地 IP）； 其次是 shared secret 与 IPSEC=No；再往后才是授权规则（ISE 默认 deny，没有授权规则即使认证成功也不放行）； 最后看 event log 的三段——端口接入、EAP 认证完成、放行入网，哪一段没出现就定位在哪一段。

Q4：SAML 和 RADIUS 什么时候用哪个？

一句话：SAML 管「人进 VPN / 管理员进 Dashboard」，RADIUS 管「设备进端口或 SSID」； 原生 SAML 的覆盖范围只有 AnyConnect VPN（p.295、p.346）。

可展开：802.1X 需要端口级 Accept/Reject、授权结果下发和 CoA， 这些是 RADIUS 的职责，SAML 断言给不了； 两个都要满足时就同时上 ISE 和 Duo（p.290）。另外 RADIUS 路径没有 inline enrollment， 用户要事先注册，这一点会影响选型。

Q5：ISE 里「认证通过」为什么还不通？

一句话：ISE 的默认授权策略是 deny，认证只解决「你是谁」， 授权规则（AD 组的 ExternalGroups → PermitAccess）才解决「你能进」（p.336、p.338）。

可展开：这个模型本身就是最小权限的落地——默认拒绝、按组授予。 如果没有这条授权规则，用户会被「认证成功但被拒」这种反直觉状态困住。

Q6：Duo 挂了会不会全员登不上？

一句话：取决于 failmode——safe 主认证成功即放行， secure 直接拒绝（p.349）。

可展开：这是典型的安全与可用性取舍， 没有通用答案，取决于业务能否接受「认证服务故障 = 全员断网」。 回答时说明你会在生产环境选哪个、为什么，比背定义更有分。

i

书里对「该选哪套」的最终态度（p.381）： AnyConnect VPN 走 SAML + Duo； client VPN / 有线 / 无线走 RADIUS + ISE + 客户端证书作第二因素—— 理由是 ISE 大幅简化 PKI，且日志与排障能力最强。 这个结论可以直接当作「选型题」的标准答案骨架。
